# P11.5 Grammar Kit — one inspector, one digit map, one chip, one hash: the V3 keyboard-compact inspector replaces `InspectorPane` in place, the D21 registry is shell constants layered under `digit-key` cell overrides, the BP-7 V2 row/card/tile kit re-skins Tasks/Library/Search, and VALUE_HEX is FNV-1a over the display string into one frozen 9-hue table

Building on the landed P11 spine (p11-spine-model.md; commits `eab9cc2…3727874`)
and the shipped shell (`shell/macos/Sources/{Window,Calendar,Commands,Tokens}.swift`).
P11.5 is **THE GRAMMAR KIT** (blueprint-assessment.md §4:315-321): the visual and
keyboard grammar of BP-1 (`bp1-inspector.html`, the 33-badge spec of record) and
BP-7 V2 (`bp7-files-library.html` + its consumers bp6/bp3/bp12), rendered native
in the lotus palette, mounted **in place** on existing surfaces. It is
**shell-only**. All five P11 seams are implemented in `ffi/src/lib.rs` and
declared in `shell/macos/lotus.h:101-128` (`lotus_cycle_date_role_at`,
`lotus_set_span_at`, `lotus_status_options_at`, `lotus_add_status_option_at`,
`lotus_distinct_values_at`), and the enriched catalog + snapshot re-base already
ship (`build_properties` ffi:449, PropertyRow ffi:104-123, OptionRow ffi:87-99,
EntityRow ffi:126-153). **Rust work in P11.5 is zero** — the one candidate (a
backlinks projection) is decided shell-side (§2.7), and the one possible
exception (definition birth on create-new property, §2.4) is verified, not
assumed, before any Rust is written (memory: test-drive-core-changes).

Delegated rulings in force, applied here: **R2** — one global shortcut map; the
full editor arrives in P19, P11.5 ships the registry + defaults
(blueprint-assessment.md §5-R2:400-408). **R3** — VALUE_HEX is ONE deterministic
hash + ONE shared seed table, frozen after this pass (§5-R3:410-412).

Every visible slice is **mockup-first**: a static exhibit cloned from the
relevant blueprint (BP-1 kind tab / BP-7 row table / BP-6 list / BP-3 results),
re-hued to the lotus palette (`Tokens.swift`), and approved against the
blueprint screenshots before a line of Swift — the owner's copy-exactly rule
(memory: copy-liv-exactly). What varies per kind is data, never the anatomy
(bp1 badge 20, entry 685).

## 1 · The load-bearing decisions

1. **The V3 inspector replaces `InspectorPane` in place** — same struct name,
   same two mounts: the standalone right pane (Window.swift:1007) and the
   calendar's embedded column (Calendar.swift:181, `topPadding: 0`). No new
   mount points, no parallel component, no feature flag. The P5 inspector's
   alphabetical every-property sheet (Window.swift:2713-2726) is retired by the
   same commit that ships its successor.
2. **One row anatomy, four cells, fixed order** — digit hint (20pt) · key
   (icon + label, 84pt) · value (flexible) · row menu (16pt); 30pt resting,
   36pt focused with accent-soft fill + inset ring (bp1:92-102, badge 1). Six
   kinds tune only *which rows are core*; the grid never forks (bp1 rule 6,
   line 235).
3. **The D21 registry is shell constants + `digit-key` cell overrides.** P11
   seeded the display-attribute *definitions* with zero *values*
   (services/src/lib.rs:84-111; p11-spine-model.md §6.1:483-487), so the
   canonical defaults (§3.2) live as one frozen Swift table; a `digit-key` cell
   on a property definition is an explicit user grant and **wins** over the
   defaults. Same layering law for icon, core-on-kind, hide-on-kind,
   hide-when-empty (§3.1). Cells are written by P19's editor (and nothing in
   P11.5 writes `digit-key`); the registry is the single map the inspector,
   search facets (D22 pass), and settings all consult (R2).
4. **Digit hints default to `hover`** — the app default per bp1 badge 8 (entry
   665); the blueprint pins `always` only for review. Setting:
   `hover / always / off`, display-only, never a behavior fork.
5. **VALUE_HEX = FNV-1a 64 over the NFC-normalized UTF-8 display string,
   mod 9, into the frozen table** `rose f43f5e · amber f59e0b · sky 0ea5e9 ·
   violet 8b5cf6 · orange f97316 · cyan 06b6d4 · blue 3b82f6 · lime 84cc16 ·
   pink ec4899` (byte-identical in bp7:14-15, bp6:21, bp3:25, bp12:25).
   Shell code, beside `Tokens.swift`, **frozen after this pass** (R3). The box
   carries only per-option `hue` override cells (p11-spine-model.md
   §10.3:777-779). Collisions are allowed by law (bp12 a15:638).
6. **The chip-hue law is enforced by types**: VALUE_HEX hues appear ONLY on
   metadata value chips (project/subject/people/area). Dates, recurrence and
   tier render neutral; status renders in its option's vocabulary hue, never
   VALUE_HEX (bp7 a19-a20:746-747; bp12 a5:606). The one blueprint
   self-contradiction (bp3:540) is ruled in §9.1.
7. **Chips are colorful always-on.** The lotus "one accent + five status dots"
   budget was annulled by the Liv pivot; BP-7 V2 is chip-forward and bp12 a5
   makes hue *mean* something ("only VALUES carry hue, so color always means
   metadata value"). No opt-in toggle ships (reconciles liv-ui-map §6-23 per
   assessment §5-R3).
8. **Density budgets are initializer shapes, not conventions.** `ObjectTile`
   has no status parameter — a board tile *cannot* render status because the
   column carries it (bp7 a25:752, bp6 a29:744, restated bp1:706). `ObjectRow`
   takes exactly one anchor chip. Illegal states unrepresentable.
9. **Re-skin now: Tasks, Library, Search** (`taskRow` Window.swift:2380,
   `indexRow` :2574, `resultRow` :2103 — the three mounts assessment §4 names).
   **Wait: Today and the calendar day panel** — Today's daily-notes rework is
   P12 (assessment §4; memory: today-capture-rework), and the day panel re-bases
   with the span-bar work (P14, fed by `due_end`). `EntityLine`
   (Window.swift:1576) survives only on the waiting surfaces and dies with them.
10. **Chip click = search navigation.** Search is navigation
    (Window.swift:1898); a value-chip click anywhere runs `<property>:<value>`
    through the existing one engine and lands on Results. Alt+click exclude
    waits for the D22 filter-panel pass (it is specified as part of that engine,
    bp3 a24:744).
11. **The wire stays snake_case.** The shell already decodes with
    `.convertFromSnakeCase` (Window.swift:238), so the P11 fields
    (`digit_key`, `hide_when_empty`, `hide_on_kinds`, `core_on_kinds`,
    `for_types`, `due_end`, `positioned_by`) land as `digitKey` etc. with zero
    Rust change. Design §7.2's camelCase wording is the doc bug, not the code
    (p11-spine-model.md §7.2:557-562 to be corrected).
12. **All P11-added decode fields are Optional in Swift.** `applySnapshot`
    decodes with `try?` (Window.swift:239) — one missing required key silently
    kills the *entire* snapshot. Optionals + defaulting accessors keep every
    old fixture and every future additive field harmless (§6).
13. **The row kit never keys behavior off `positioned_by` for task-ness.** The
    code pinned DATE-first positioning (calendar_set `[date, due]`,
    services/src/lib.rs:346; ffi test :2183), contradicting design §7.3's
    due-first wording. The task checkbox draws off kind + status vocabulary
    (as `taskStatusToggle` already does, Window.swift:1877), so a task carrying
    both `due` and `date` is unaffected. §7.3's wording gets fixed; no code
    bends.
14. **Deferred from BP-1 v1, decided (§2.8): presets, the AI suggestion card
    (and its wand), the destination line, and row-menu "Change type".** Each
    has a named reason — missing substrate, not missing will.

### 2.2 Row anatomy — `PropertyRowView`

One SwiftUI row, four cells, `grid 20 · 84 · 1fr · 16` at 7pt gaps (bp1:92):

- **kbd cell (20pt):** the registry's key for this property name, rendered per
  the hint setting; unassigned renders the dashed `·` blank (bp1:101) and stays
  reachable via ↑↓ only. Focused row recolors the kbd to accent (bp1:102).
- **key cell (84pt):** 16pt SF Symbol (the `icon` attribute when a cell exists
  on the definition; else the kind-default symbol) + the property label.
- **value cell (1fr):** dispatched by kind — chips (`ValueChip`, §4.1) for
  multi-value/select/reference, plain text/number, the **role pill** for
  datetime rows (solid accent = calendar role, dashed muted = lookup roles,
  bp1:104-105), a `.rec` recurrence tag when the row's property anchors a
  recurrence, monospace for email/phone-shaped text, and the dashed **ghost**
  CTA for empty core rows (`+ set status`, `add to project` — bp1:109,
  badge 11: zero fill-pressure).
- **menu cell (16pt):** the `⋯` button, opacity 0 at rest, fades in on hover
  (bp1:94-95); opens the row menu (§2.6).

Focus = accent-tint fill + 1.5pt inset accent ring + min-height 30→36
(`Theme.accentTint`, `--ctl` 36, bp1:96). Hover = background tint + `⋯`
fade-in, opacity/tint only, nothing moves (entry 676). Row order: core rows in
the core table's order (§3.2); MORE rows alphabetical.

**Date rows.** Every datetime role property with a cell renders its own row
(two on a warranty file: purchased-on + valid-until, both dashed lookup —
badge 25, entry 699). The role pill click / Space cycles through
`lotus_cycle_date_role_at` (lotus.h:105; one lossless transaction, refusal =
shake, the seam returns the NEW role name for optimistic paint). A span renders
`start → end`. ⏎ opens the full date editor (§2.4).

### 2.3 Digit choreography — Commands.swift integration, scoped

The registry integration uses the existing machinery, nothing parallel:

- **Global commands** (registered in `registerCommands`, Window.swift:1289):
  `inspector.focus` = Alt+→ (focus the panel, landing on the last-edited row,
  else the first core row) and `inspector.blur` = Alt+← (return to the doc,
  cursor restored) — badge 32, entry 673. These are ordinary `CommandDef`s
  (Commands.swift:88).
- **While the panel holds focus**, it pushes a capture scope
  (`CommandRegistry.pushCaptureScope`, Commands.swift:132) allowing only
  inspector command ids — the §2.28.2 keyboard-scope mechanism, already built.
  Inside the scope: digits `1…0` jump to the mapped row **and open its
  editor** (opening MORE first when the row is folded — badge 14: "pressing 3
  on the task tab opens MORE and focuses subjects"), `N` add-property, `M`
  toggle MORE, `H` row menu, `F2` rename, `↑↓` row nav, `⏎` edit, `Esc` closes
  the open editor first, then unfocuses the panel. Popped on blur.
- **Editors are text fields**, so while one is open the registry's
  bare-key/textFocused guard (Commands.swift:189) keeps digits typable — the
  digit-picks-inside-the-status-popover behavior is the popover's own local
  key handling, not registry commands.
- Task-fields letters `D/P/R` (badge 16) and the view-config letters
  `L/F/G/S/W` register in the same map; the view letters stay dormant until
  views become objects (§8).

The four-keystroke promise is the acceptance test: **Alt+→ · 3 · type · ⏎**
files a note (bp1 hintcol).

### 2.4 Anchored editors — value pool, status, date, add-property

All four are one popover shape: anchored to the focused row (SwiftUI
`.popover`, preferred edge toward the content pane; AppKit may flip it), a
search field with type-to-filter, then a result list — bp1 `.pop`:127,
badge 9.

**Value pool (chips / selects / relations / people — badge 9, entry 666).**
Pool order is the D08 three-tier law (bp1:300):
① *this vault* — `lotus_distinct_values_at(path, property)` (lotus.h:128),
fetched once on open through the box queue (never per keystroke; type-to-filter
is client-side), rendered `value · in vault · <count> · ⏎ add`;
② *seeded set* — the definition's `options` from the catalog (OptionRow), for
select-kinds, labelled `seeded`, filtered by `for_types` against the entity's
kind;
③ *create* — `Create "<typed>"` on Ctrl+⏎. The create leg writes through
`lotus_set_at` / `lotus_add_cell_at` for text/tag kinds. For select kinds,
creating a new *option entity* has a seam only for status
(`lotus_add_status_option_at`); generic select-option birth is **deferred**
(§8) — the pool for those offers tiers ① and ② only. ⏎ adds, Esc closes.
Project chips display the leaf only (badge 9).

**Status picker (badge 17, entry 680).** Cap `status · digits pick`; rows =
`lotus_status_options_at(path, kind)` in board order, each with its kbd digit,
its hue dot, its name; digits pick, ⏎ confirms, Esc closes. Single-select: a
pick is one `model.set(id, "status", name)` (`status:<name>` writes a
`Value::Select`, design §7.1) — replacing, so a future board column moves on
the same write. The separator row `New option… Ctrl+⏎` rides
`lotus_add_status_option_at` (hue argument −1 = none; the option gets its hue
in the vocabulary editor, a BP-6 board-pass feature — "Edit vocabulary…" is
deferred to it, §8). Empty status renders the ghost, never a default (badge
11: status exists on every kind, empty is valid).

**Date editor (badge 23, entry 695).** Cap `date role · Space cycles`; the
four-role list with the current role checked (`calendar · renders on
calendar`; the three lookups labelled `lookup`); Space cycles via
`lotus_cycle_date_role_at`; then cap `span` with start field → optional end
field bearing ✕; writes ride `lotus_set_span_at(path, id, property, start,
end, dateOnly)` — end 0 collapses to a plain date, end ≤ start is refused
before the box opens (lotus.h:111, content.rs:760-772; refusal = shake, no
toast). The `Repeat… R` line displays the existing recurrence state and writes
through the recurrence property the P11 engine already reads
(services/src/recurrence.rs — unchanged; recurrence anchors on the positioning
set, so repeat is available on ANY dated row, badge 23's hint). ⏎ saves, Esc
reverts. A contact birthday is just this row with role=calendar + yearly
repeat — no special feature (badge 21).

**Add-property (`N` row — badge 13, entry 670).** Type-ahead over the catalog
ranked by `usage` descending, each rendered `name · kind · on <usage> objects`;
separator; `Create "<typed>" as new property` on Ctrl+⏎. Selecting an existing
property focuses (or reveals) its row with the editor open. The create leg
assumes the core births a definition on first `lotus_set_at` with an unknown
property name ("exists vault-wide the moment one object uses it", entry 670).
**That assumption is verified with a failing test before the slice is built**;
if the core refuses unknown names, this becomes the single Rust exception in
P11.5 (a thin `lotus_add_property_at`) and is flagged at review — do not trust
the doc's reasoning (memory: test-drive-core-changes).

### 2.5 MORE / core / hide-when-empty — the resting-state law

Row placement is a pure function of (core table §3.2, display-attribute cells,
the entity's cells, `usage`):

1. **Core rows** — properties named by the kind's core set (`core_on_kinds`
   cell if present, else the shell default table) **always render**, empty
   included (ghost/placeholder) — the core card is the promise (badge 14).
   A `hide-on-kind` cell naming this kind removes a row from this kind
   entirely (badge 26).
2. **Non-core rows with a value** → MORE, alphabetical.
3. **Non-core empty rows** → hidden when hide-when-empty is on — and it
   defaults **on** (badge 14: it "is what keeps the resting panel short");
   a `hide-when-empty=false` cell on the definition surfaces them in MORE.
   Hidden rows stay reachable through `N` (add-property) and through their
   digit (which opens MORE and materializes the row focused).
4. **MORE · N** header with rotating chevron; `M` toggles; collapsed is the
   resting state; digits reach collapsed fields (D11's law).

`usage` does not gate visibility — it ranks pools and the `N` type-ahead
(§2.4). The P5 behavior of synthesizing a row for *every* catalog property
(Window.swift:2708-2726) dies here; that sheet is what MORE + hide-when-empty
replace.

### 2.8 Deferred from BP-1 v1 — decided, with reasons

- **Preset row (badge 5, Alt+P).** A preset is a named bundle of rows +
  vocabulary seeds that must never overwrite filled values — that is a
  substrate (preset entities, an apply transaction) no P11 seam provides, and
  P11.5 is sworn to ~zero Rust. It is also D22-adjacent (presets searchable
  from the filter panel). Defer whole; the `.presetrow` slot in the layout
  stays unrendered so the mockups diff cleanly when it lands.
- **AI suggestion card + header wand (badges 6/7, Alt+M).** The per-field
  suggester needs a suggestion seam (values from vault + seeded pools, apply
  on Accept only). Lotus's proposals inbox is a different surface (capture
  classification). The amber AI-presence hue is already reserved
  (`Theme.warning`, Tokens.swift:33-34) and waits for it. Defer to the AI
  pass; ships with the same popover/chip primitives this kit builds.
- **Destination line (badge 4).** See §9.2 — lotus stores entities in a box
  log, not per-object vault files; there is no truthful path to render and
  the row's promise (click reveals in the vault tree) cannot be kept.
  Deferred until the projection/export story gives objects a real path.
- **Row-menu "Change type ▸" (badge 26, one item).** A definition-kind change
  forces a vault-wide value re-parse/refusal story the core does not have.
  One item on one menu; the rest of the menu ships. Defer to the schema pass.
- **F2 rename, trash-undo, row hover, footbar all SHIP** — they cost nothing
  and the blueprint names them as the floor.

## 3 · The D21 digit map (R2)

### 3.1 Registry shape — one map, one layering law

```swift
// DigitMap.swift — THE one global map (R2). Keyed by property NAME.
struct DigitMap {
    static let defaults: [String: Key]   // §3.2, frozen shell constants
    // resolve(catalog) → [String: Key], recomputed per snapshot:
    //   1. start from defaults
    //   2. overlay digit-key cells (PropertyRow.digitKey) — a cell WINS;
    //      the displaced default's property goes blank '·'
    //   3. two cells claiming one key → lowest definition id wins,
    //      the loser renders '·' (deterministic, no double-fire)
}
```

The registry is a pure function of the catalog — no stored state, no
migration. Kind-tuning changes a row's *visibility* (core vs MORE), never its
key (badge 8: "STABLE across all six kinds"). The same map is what the search
palette's facet toggles will consult in the D22 pass and what P19's Settings →
Shortcuts editor will *edit* (by writing `digit-key` cells — the box is the
override store, the registry is the reader). Nothing in P11.5 writes
`digit-key`.

The same three-layer law (shell default table → definition cell → render)
resolves **icon**, **core-on-kind**, **hide-on-kind**, and **hide-when-empty**
— one law, five attributes, because P11 seeded all five definitions with zero
values (services/src/lib.rs:87-111).

### 3.2 The canonical defaults (frozen with this doc)

Digits, read off all six BP-1 tabs (badge 8, entry 665):

```
1 form · 2 type · 3 subjects · 4 project · 5 area · 6 people · 7 tier
8 date · 9 status · 0 description · N new/add-property
```

Letters: `D` due, `P` priority, `R` repeat (task fields, badge 16);
`L` lens, `F` filters, `G` group-by, `S` sort, `W` fields (view config,
bp1:617-625 — registered, dormant until views are objects). `M` MORE,
`H` row menu, `F2` rename, `Alt+→/←` focus/blur. bp6 a23's question (are
task fields a task-local digit block?) is answered by R2: **one map** — task
fields take letters, digits never re-bind per kind.

Core sets per lotus kind (BP-1's six cores, contact→person; properties absent
from the catalog simply don't render — the table names candidates, not
obligations):

- **note / default** (bp1:261-345): form, type, subjects, project, area,
  people, tier, date, status, description.
- **task** (bp1:347-411): type, project, area, people, tier, status,
  description + the Task-fields group (due, priority, repeat); form and
  subjects fold to MORE **keeping digits 1 and 3**.
- **person** (bp1:413-465): type, role, org, email, phone, subjects, area,
  birthday-date, status, description; form/project/tier → MORE.
- **event** (bp1:467-531): type, subjects, area, people, tier, date, status,
  description; form/project → MORE.
- **file** (bp1:533-599): type, subjects, area, date, valid-until, tier,
  status, sources, description; form/project/people → MORE.
- **project / list**: the note base set, until a blueprint says otherwise.

### 3.3 Hints + conflicts

Hint display: `hover` (default) · `always` · `off` — a UserDefaults setting,
pure display (badge 8). Conflict handling is §3.1's two rules (cell beats
default; lowest-id cell beats cell) — deterministic, rendered honestly: a
displaced row shows `·` and remains ↑↓-reachable, exactly like a never-assigned
row. No dialogs, no warnings; P19's editor is where conflicts get *resolved*.

## 4 · The BP-7 V2 row kit

### 4.1 Components — the budget as code

Five views in one file (`RowKit.swift`), consumed by three surfaces:

- **`ValueChip(text, hue, icon?, dot?)`** — THE chip (bp7:150-160): pill,

## 5 · VALUE_HEX (R3) — one hash, one table, frozen

### 5.1 The function

```swift
// Hues.swift — beside Tokens.swift. FROZEN after this pass (R3).
func valueHex(_ display: String) -> Color {
    // 1. NFC-normalize; UTF-8 bytes. No case folding, no trimming —
    //    the input IS the display string (lotus_views::display) exactly as
    //    it appears in CellRow.value / distinct-values / option names,
    //    so chips, facets, graph and tree dots agree by construction.
    // 2. FNV-1a 64: offset 0xcbf29ce484222325, prime 0x100000001b3.
    // 3. index = hash % 9 → SEED[index].
}
```

FNV-1a is chosen for being trivially portable — if a service helper ever needs
the same hue, the constants copy in one line and stay bit-identical. Collisions
are allowed by law ("9–12 hues", bp12 a15:638). A unit test pins known
string→index vectors; changing them after this pass is a spec break, not a
tweak.

### 5.2 The seed table

The nine `--vx-*` hexes, byte-identical across bp2/3/5/6/7/8/10/12/14, become
`static let SEED: [NSColor]` — `#f43f5e #f59e0b #0ea5e9 #8b5cf6 #f97316
#06b6d4 #3b82f6 #84cc16 #ec4899` — **theme-independent** (the same hue in
light and dark; only the chip's bg/ink mixes are scheme-aware, §4.1). Shell
code, not box data: the spine's recommendation (assessment §2.4:194,
p11-spine-model.md §10.3), and the R3 ruling makes it final.

### 5.3 Overrides + the color budget

Hue resolution for any chip/dot: **per-option `hue` cell (OptionRow.hue,
degrees) → else VALUE_HEX(display) for metadata values → else neutral for the
never-VALUE_HEX classes** (dates, recurrence, tier, status-without-hue). The
seeded status hues (todo 210° / doing 45° / done 145°,
services/src/lib.rs:163) are ordinary override data R3 may re-edit; nothing in
the shell hardcodes them. Color budget: chips are colorful **always-on**
(decision 7) — hue always means metadata value, objects render neutral, type
is an icon. There is no toggle to explain because there is no state in which
color lies.

## 6 · Swift decode — additive, optional, `try?`-safe

The decoder already uses `.convertFromSnakeCase` (Window.swift:238,:258), so
the wire stays snake_case (decision 11) and the structs gain camelCase fields.
**Every P11 field is Optional with a defaulting accessor** — `applySnapshot`'s
`try?` (Window.swift:239) means one missing required key silently drops the
whole snapshot, so optionality is resilience, not politeness:

```swift
struct OptionRow: Codable, Hashable, Identifiable {
    let id: UInt64
    let name: String
    let order: Double?        // wire always emits; optional for old fixtures
    let hue: Double?          // wire emits null when no override — genuinely nil
    let completes: Bool?
    let forTypes: [String]?   // wire: for_types; [] = offered everywhere
    var boardOrder: Double { order ?? 0 }
    var isTerminal: Bool { completes ?? false }
}

struct PropertyRow: Codable, Identifiable, Hashable {
    let id: UInt64            // = the definition ENTITY id (row-menu writes)
    let name: String
    let kind: String
    let options: [OptionRow]
    let usage: Int?           // live-carrier count; nil → 0
    let icon: String?
    let digitKey: String?     // wire: digit_key — the R2 override cell
    let hideWhenEmpty: Bool?  // nil → the shell default (true)
    let hideOnKinds: [String]?
    let coreOnKinds: [String]?
}

// EntityRow adds exactly two (both genuinely optional on the wire):
    let dueEnd: Int64?        // wire: due_end — span end, absent for plain dates
    let positionedBy: String? // wire: positioned_by — absent when undated
```

New seam payloads get their own structs + the same snake_case decoder; they
are new seams with no legacy payloads, so required is safe:

```swift
struct StatusOption: Codable, Identifiable {   // lotus_status_options_at
    let id: UInt64; let name: String; let order: Double
    let hue: Double?; let completes: Bool
}
struct DistinctValue: Codable {                // lotus_distinct_values_at
    let value: String; let count: Int
}
```

`BoxModel` grows thin wrappers on the box queue, mirroring `set`/`unset`:
`statusOptions(kind:done:)`, `addStatusOption(kind:name:hue:done:)`,
`distinctValues(property:done:)`, `cycleDateRole(id:property:done:)` (done
receives the new role name), `setSpan(id:property:start:end:dateOnly:done:)` —
each a `lotus_*_at` call + `refresh()` on write, the
refresh-after-every-act law (Window.swift:139).
